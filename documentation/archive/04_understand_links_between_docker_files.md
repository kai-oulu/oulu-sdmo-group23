### How Dockerfile, docker-compose.yml, ci.yml are linked - clear breakdown

Think of 3 different **runtimes**: Local dev, GitHub Actions (after commits), Docker deployment. Different files apply in each.

#### 1. What each file IS and WHEN it runs

**`Dockerfile` - Blueprint for ONE container image**
- What: Instructions to build a container image: `FROM python:3.13-slim` (matches `.python-version` 3.13), `COPY pyproject.toml uv.lock .python-version README.md`, `RUN pip install uv && uv sync --frozen --no-install-project` (creates `.venv` with locked `cryptography`, `mlkem` from `uv.lock`), `EXPOSE 5000 5001 6000 6001`, `HEALTHCHECK`, `CMD ["python", "src/edge_gateway.py"]` (default gateway, overridden for cloud)
- When used:
  - **Local:** When you run `docker build -t edge-gateway:test .` or `docker-compose up --build` (compose builds from Dockerfile)
  - **CI:** In `ci.yml` job `docker-build`, step `docker build -t edge-gateway:test .` - CI builds same Dockerfile to verify it works
- Not used when you run locally via `uv run python src/edge_gateway.py` (that's direct Python, no Docker)

**`docker-compose.yml` - Orchestrator for MULTIPLE containers (local deployment simulation)**
- What: Defines 2 services that both **build from same Dockerfile**:
  - `cloud`: `build: .` + `command: python src/cloud_service.py` + ports `6000:6000, 6001:6001` + env `CLOUD_PK_PATH=/app/shared/cloud_public_key.bin` + volume `pqc-shared:/app/shared`
  - `gateway`: `build: .` + `command: python src/edge_gateway.py` + ports `5000:5000, 5001:5001` + env `CLOUD_HOST=cloud` (Docker DNS, not 127.0.0.1) + same shared volume + `depends_on: cloud healthy`
  - Volume `pqc-shared`: named volume for sharing `cloud_public_key.bin` (800B, generated by cloud on startup), `telemetry.db` (created by cloud `init_db()`), `gateway_fallback.log` (created by gateway when fallback)
- When used:
  - **Local ONLY:** `docker-compose up --build` - simulates deployment locally (per course Q&A: "entire pipeline is simulated, just code", no real cloud hosting needed)
  - **NOT used in CI:** CI does `docker build`, not `docker-compose up` (CI just verifies images build, doesn't run full stack)
- Sensor flow in Docker: `[Host: python src/legacy_device.py]` → host `127.0.0.1:5000` → Docker forwards to gateway container `5000` → gateway PQC encaps → forwards to `cloud:6000` via Docker network (CLOUD_HOST=cloud) → cloud stores in DB

**`.github/workflows/ci.yml` - Automation that runs AFTER commits (GitHub Actions only)**
- What: GitHub Actions workflow, runs in GitHub's cloud runners after you push
- When:
  - On `push` to `main` or `arena/*` branches (your branch `arena/04f59b2c-...`)
  - On `pull_request` to `main`
  - **NOT used locally** unless you run `act` tool or manually run same commands
- Jobs linkage:
  ```yaml
  jobs:
    test:  # Job 1 runs FIRST
      steps: checkout → setup-uv (reads .python-version + uv.lock) → uv sync --frozen (respects pyproject.toml + uv.lock) → uv run pytest -v (33 tests) → PQC round-trip → import check
    docker-build:  # Job 2 runs AFTER test
      needs: test  # ← only runs if test succeeds (33 passed), fail-fast
      steps: checkout → docker build -t edge-gateway:test . (builds from Dockerfile) → docker build -t cloud-service:test .
  ```
  - So **test block runs first**, then **docker-build block runs** (sequential dependency via `needs: test`)
  - If tests fail, docker-build never runs

#### 2. How they are linked together

```
pyproject.toml + uv.lock + .python-version + README.md
        ↓ (COPY in Dockerfile)
Dockerfile (blueprint for ONE image, uses uv sync --frozen to install locked deps)
        ↓ (build: . in compose)
docker-compose.yml (orchestrates 2 images from SAME Dockerfile: cloud + gateway, with ports, env vars, shared volume pqc-shared)
        ↑
        | (CI verifies Dockerfile builds)
.github/workflows/ci.yml (GitHub Actions only, after commits)
        | - test job: uses same pyproject.toml+uv.lock+.python-version via setup-uv + uv sync --frozen + pytest
        | - docker-build job: needs test, runs docker build -t ... . (same Dockerfile) to verify it builds
```

- **Dockerfile is the link:** Both CI (`docker build`) and local (`docker-compose up`) build from **same Dockerfile**, so CI verification ensures compose will also build
- **ci.yml does NOT use docker-compose.yml:** CI only does `docker build`, not `docker-compose up` (compose is for local deployment simulation)
- **pyproject.toml + uv.lock + .python-version are used EVERYWHERE:**
  - Local: `uv sync --frozen` reads them to create `.venv` with locked versions
  - CI: `setup-uv` reads `.python-version` (3.13), `uv sync --frozen` reads `pyproject.toml` + `uv.lock`
  - Docker: `COPY pyproject.toml uv.lock .python-version README.md` + `uv sync --frozen` inside container

#### 3. Which files apply where - table

| File | Local direct run (`uv run python src/...`) | Local Docker (`docker-compose up`) | GitHub Actions (after push) |
|------|--------------------------------------------|------------------------------------|-----------------------------|
| `pyproject.toml` | ✅ Yes (`uv sync`) | ✅ Yes (COPY in Dockerfile + uv sync) | ✅ Yes (uv sync --frozen in CI) |
| `uv.lock` | ✅ Yes (`uv sync --frozen`) | ✅ Yes (COPY + uv sync --frozen) | ✅ Yes (setup-uv + uv sync --frozen) |
| `.python-version` | ✅ Yes (uv reads 3.13) | ✅ Yes (FROM python:3.13-slim matches, COPY) | ✅ Yes (setup-uv reads) |
| `src/*.py` | ✅ Yes (direct) | ✅ Yes (COPY src/ in Dockerfile) | ✅ Yes (import check + pytest) |
| `tests/` | ✅ Yes (`pytest -v`) | ❌ No (not needed in container) | ✅ Yes (pytest -v in CI) |
| `Dockerfile` | ❌ No (unless you build) | ✅ Yes (`build: .`) | ✅ Yes (docker build in CI) |
| `docker-compose.yml` | ❌ No | ✅ Yes (orchestrates cloud+gateway) | ❌ No (CI only does docker build, not compose up) |
| `.github/workflows/ci.yml` | ❌ No (only GitHub Actions) | ❌ No | ✅ Yes (runs after commits) |
| `cloud_public_key.bin`, `telemetry.db`, `gateway_fallback.log` | Generated at runtime (gitignored) | Generated inside shared volume `pqc-shared` at `/app/shared/...` | Generated at runtime in CI runner (ephemeral, discarded after job) |

#### 4. Sensor sending data - is it via test files?

- **No, not via test files.** Tests use `running_gateway` fixture that starts gateway on ephemeral port via `subprocess.Popen`, not Docker, and sends packets via `socket.create_connection` in test functions. Tests don't use `legacy_device.py` main, they use `legacy_device.encrypt_payload` directly.
- **Real sensor flow:**
  - **Local without Docker:** `python src/legacy_device.py` (ephemeral client) → TCP to `127.0.0.1:5000` → gateway (5000) → PQC forward to cloud `127.0.0.1:6000` → cloud DB
  - **Local with Docker:** Gateway container exposes `5000:5000`, so host legacy `python src/legacy_device.py` connects to host `127.0.0.1:5000` → forwarded to gateway container → gateway connects to `cloud:6000` via Docker DNS (env `CLOUD_HOST=cloud`) → cloud container
  - **Docker-compose does NOT include legacy_device as service** because it's ephemeral (runs once and exits). You run it manually on host after `docker-compose up`.

**Summary:** `ci.yml` = GitHub Actions only (after commits), runs test first then docker-build (needs test). `Dockerfile` = blueprint used by both CI (docker build verification) and local (docker-compose build). `docker-compose.yml` = local only (deployment simulation), uses same Dockerfile for 2 services, shares files via named volume `pqc-shared` (robust, no need host files exist beforehand). `pyproject.toml`+`uv.lock`+`.python-version` are used in all three runtimes for reproducibility.

### How `ci.yml` and `docker-compose.yml` read `Dockerfile` without mentioning it - implicit convention

You’re right, you don’t see `Dockerfile` string in the code lines (only comments). That’s because Docker has **default implicit filename** - if you don’t specify, it looks for `Dockerfile` in the build context.

#### 1. `docker-compose.yml` - `build: .`

```yaml
services:
  cloud:
    build: .   # ← this is shorthand, no Dockerfile mentioned
```

What Docker Compose actually does (implicit):
```yaml
build:
  context: .          # current directory (where pyproject.toml, Dockerfile, src/ are)
  dockerfile: Dockerfile  # ← implicit default, if not specified, looks for file named "Dockerfile" in context
```

So `build: .` = `build: {context: ., dockerfile: Dockerfile}` - it **automatically** reads `./Dockerfile` in current directory.

If you had multiple Dockerfiles, you would write explicitly:
```yaml
build:
  context: .
  dockerfile: Dockerfile.cloud  # explicit
```

But we have only one `Dockerfile`, so `build: .` is enough and implicitly uses it.

**Where does it get files from?** Dockerfile itself has `COPY pyproject.toml uv.lock .python-version README.md ./` and `COPY src/ ./src/` - so when Compose builds, it copies those files from host context (`.`) into image, then `RUN uv sync --frozen` installs locked deps.



#### 2. `ci.yml` - `docker build -t edge-gateway:test .`

```yaml
- run: |
    docker build -t edge-gateway:test .   # ← no Dockerfile mentioned, only "." 
```

What Docker CLI actually does (implicit):
```bash
docker build -f Dockerfile -t edge-gateway:test .  
# -f Dockerfile is implicit default, "." is build context (current dir)
```

So `docker build .` = `docker build -f Dockerfile .` - it **automatically** looks for `./Dockerfile` in context `.`.

If you had multiple Dockerfiles:
```bash
docker build -f Dockerfile.cloud -t cloud:test .
```

But we have one, so `.` is enough.

**Linkage:**
- Both `ci.yml` (`docker build .`) and `docker-compose.yml` (`build: .`) **implicitly** read same `./Dockerfile` because they both use current directory `.` as build context and default to file named `Dockerfile`
- That’s why CI’s `docker build` verification ensures `docker-compose up --build` will also work - same Dockerfile, same `COPY pyproject.toml uv.lock .python-version` + `uv sync --frozen`

#### 3. Summary table

| File | Code line | Implicit Dockerfile usage | Explicit equivalent |
|------|-----------|---------------------------|---------------------|
| `docker-compose.yml` | `build: .` | Looks for `./Dockerfile` in context `.` | `build: {context: ., dockerfile: Dockerfile}` |
| `ci.yml` | `docker build -t ... .` | Looks for `./Dockerfile` in context `.` | `docker build -f Dockerfile -t ... .` |

So you don’t need to write `Dockerfile` in code - Docker’s convention is: **if you give a context directory, default Dockerfile name is `Dockerfile` in that directory**. That’s how 2 files read from Dockerfile without mentioning it.

If you want to be explicit for clarity (optional), you could change to:
```yaml
# docker-compose.yml explicit
build:
  context: .
  dockerfile: Dockerfile
```
```yaml
# ci.yml explicit
docker build -f Dockerfile -t edge-gateway:test .
```
But functionally same as current shorthand.
